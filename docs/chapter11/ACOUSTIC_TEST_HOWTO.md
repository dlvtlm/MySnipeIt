**מה כן צריך:** שורת לוג אחת. פירוט בשלב 3.

## מה יש בענף `acoustic`, מאומת

| רכיב | מצב |
|---|---|
| קוד המודול, 15 קבצים | ✅ `pi-streaming/acoustic/` |
| דגלי הידור וקישור | ✅ `-D_GNU_SOURCE -Iacoustic`, `-lfftw3f -lasound -lzmq` |
| חיווט ב-`main.c` | ✅ include, שדה, start, tick, stop |
| כשל אקוסטי לא מפיל את השרת | ✅ אזהרה וממשיך |
| תיקון תקיעת ה-FFT | ✅ `FFTW_ESTIMATE` כבר בקוד |
| **טיפול בפקודות מהאפליקציה** | ✅ `ws_set_command_callback` ← `ddl_bridge_handle_command` |
| `set_servo_angles` ← סיבוב + אירוע `NOISE_DETECTED` | ✅ `ddl_bridge.c:734-759` |
| `select_target` | ✅ `ddl_bridge.c:762` |

**המשמעות:** בדיקות D3 (סיבוב בעקבות התראה) ו-C4 (נעילה) **אמורות לעבוד**. זה מבטל את
האזהרה שנתתי קודם.

**ומה שאין:** אין תוכנית עצמאית. אין `main_realtime.c`, אין `ws_reporter.c` ואין `test_harness.c`.
**הפקודה `./snipeit_acoustic` לא קיימת בענף הזה.** המודול רץ אך ורק בתוך `streaming_server`.

## שלב 1 — ודא שהמיקרופונים עובדים, חמש דקות

**עשה את זה ראשון.** אין טעם לסמן עמדות אם ערוץ שקט.

```bash
arecord -l
```

צריך להופיע כרטיס בשם `snipeit-4mic`. אם לא:

```bash
grep -iE "snipeit|i2s|dtparam=audio" /boot/firmware/config.txt
ls /boot/firmware/overlays/ | grep -i snipeit
dmesg | grep -iE "i2s|asoc|snipeit"
```

הקלט שלוש שניות וודא אות בכל ארבעת הערוצים:

```bash
arecord -D plughw:0 -f S32_LE -r 48000 -c 4 -d 3 /tmp/mic_check.wav
sox /tmp/mic_check.wav -n stat
```

**מצופה:** משרעת סבירה ולא אפס. ערוץ שקורא אפסים הוא בעיית חיווט בבורר הערוץ או בקו
הנתונים של אותו מיקרופון. שלושת הנותרים עדיין יאתרו, בדיוק נמוך יותר.

## שלב 3 — 🔴 השינוי היחיד שכן נדרש, שתי שורות

**הבעיה:** המודול בונה את ה-JSON של האירוע ושולח אותו ב-WebSocket בלבד.
**הוא לא מדפיס אותו למסך.** בדקתי את `acoustic_bridge.c` ואין שם שום הדפסה של האירוע,
רק של שגיאות. לכן `tee` על פלט השרת **לא יתפוס את הזוויות**, ולא יהיה לך לוג לניתוח.

**התיקון:** בקובץ `pi-streaming/acoustic/acoustic_bridge.c`, מצא את הבלוק סביב שורה 195:

```c
    if (n > 0 && (size_t)n < sizeof(json))
    {
        if (ws_send_json(b->ws, json, (size_t)n) != 0)
```

והוסף שתי שורות מיד אחרי הסוגר הפותח:

```c
    if (n > 0 && (size_t)n < sizeof(json))
    {
        printf("[EVENT] %s\n", json);        /* CH10 - זמני */
        fflush(stdout);                      /* CH10 - זמני */
        if (ws_send_json(b->ws, json, (size_t)n) != 0)
```

**`fflush` הוא לא קישוט.** בלעדיו הפלט נאגר ב-buffer כשהוא מופנה לקובץ ולא לטרמינל,
והשורות יופיעו בקבוצות עם חותמות זמן מטעות. זו בדיוק התקלה שכבר נתקלתם בה פעם אחת
בפרויקט, והיא מתועדת ברשומת גשר הנתונים של חבר הצוות.

```bash
make
```

**לניקוי בסיום:**

```bash
git checkout -- acoustic/acoustic_bridge.c
```

## שלב 4 — הרצת הבדיקה, שלושים וחמש דקות

### סימון העמדות

שתים עשרה עמדות בקפיצות של חמש עשרה מעלות, מרחק אחיד של שלושה מטרים מהמערך:

```
-90, -75, -60, -45, -30, -15, +15, +30, +45, +60, +75, +90
```

**כיוון האפס הוא הציר הקדמי של מערך המיקרופונים**, כלומר מרכז הקשת.
הוא אינו בהכרח הכיוון שאליו המצלמה מסתכלת, ואם הצריח מסובב אל תתבלבל.

**צלם את הסידור** לקובץ `CH10_acoustic_setup.jpg`. זו הראיה לפרוטוקול, והיא גם נכנסת לפרק.

### ⚠️ שני תנאים שבלעדיהם לא יתקבל אף אירוע

**תנאי 1: הרץ דרך `start.sh` ולא את `streaming_server` ישירות.**

השרת בודק בעלייה את נתיב הווידאו. הנתיב `/tmp/camera_stream.h264` הוא **צינור בעל שם (FIFO)
ש-`start.sh` יוצר**, ולא קובץ. הרצה ישירה של `streaming_server` נכשלת ב-
`config_probe_video` ויוצאת **לפני** שהגשר האקוסטי בכלל מנסה לעלות. זו בדיוק השגיאה
`Video file not accessible` ואחריה `Failed to probe video file`.

**תנאי 2: האפליקציה חייבת להיות מחוברת לאורך כל הבדיקה.**

ב-`acoustic_bridge.c` שורה 133 יש:

```c
/* Short-circuit when nobody is listening — saves an FFT + grid search */
if (!ws_is_client_connected(b->ws))
{
    return 0;
}
```

**כשאין לקוח מחובר, האירוע נזרק לפני שמתבצע חישוב כלשהו.** לא מחושבת זווית, לא נשלח JSON,
והשורה שהוספת בשלב 3 לא תודפס. אין שום דרך לדעת מהלוג שמחאת כף בכלל נקלטה.

לכן: **הפעל את האפליקציה בטאבלט, התחבר למכשיר, והשאר את הדשבורד פתוח לאורך כל שישים
המחיאות.** ודא שמחוון LINK ירוק לפני שאתה מתחיל.

### ההרצה

```bash
cd ~/SnipeIt/pi-streaming
./start.sh 2>&1 | tee ~/CH10_acoustic_hw.log
```

חפש בעלייה את השורה:

```
[ACOUSTIC] Started — 4-mic array, 48000 Hz, threshold 10.0
```

**אם מופיעה במקומה** `WARNING: acoustic bridge failed to start`, המודול לא עלה. חזור לשלב 1.

לאחר מכן חבר את האפליקציה והמתן ל:

```
[MAIN] System ready!
```

**רק כשהאפליקציה מחוברת התחל למחוא כפיים.**

בכל עמדה:

1. עמוד בעמדה המסומנת.
2. אמור בקול את מספר העמדה ואת הזווית, למשל "עמדה ארבע, מינוס ארבעים וחמש".
3. מחא כפיים **חמש פעמים**, לפחות **שתי שניות** בין מחיאה למחיאה.
   זמן העצירה הוא חצי שנייה, ומרווח קצר מדי יבלע אירועים.
4. המתן חמש שניות ועבור לעמדה הבאה.

**סה"כ שישים אירועים.**

כל אירוע יופיע בלוג כך:

```
[EVENT] {"type":"acoustic_event","timestamp_us":...,"azimuth_deg":-44.0,
         "confidence":0.87,"peak_amplitude":0.9123,"duration_ms":3.2,"valid":true}
```

### אם מחיאת כף לא מפעילה את הגלאי

שתי אפשרויות. או מקור חד יותר, כמו בלון שמתפוצץ או שני קרשים, או הורדת הסף:

```bash
sed -i 's/#define ONSET_THRESHOLD     10.0f/#define ONSET_THRESHOLD     5.0f/' acoustic/acoustic_config.h
make
```

**אם הורדת את הסף, רשום זאת בדוח.** הערך המשוגר הוא 10.0 וכל סטייה חייבת להיות מתועדת.

## שלב 5 — ניתוח, עשר דקות

```bash
scp pi@<כתובת ה-Pi>:~/CH10_acoustic_hw.log .
grep '\[EVENT\]' CH10_acoustic_hw.log | wc -l     # צריך להיות בערך 60
```

בנה טבלה:

```
עמדה | זווית אמת | זווית מוחזרת | סטייה | confidence | valid
```

**חשב שני מספרים בנפרד ורשום את שניהם:**

- **הסטייה הממוצעת** על פני כל האירועים
- **הסטייה המרבית**, כלומר המקרה הגרוע ביותר

זו השאלה שהדוח חייב לענות עליה, משום שהטענה הקיימת על חמש מעלות אינה מציינת
אם היא ממוצע או מקרה גרוע.

**אם התוצאה חורגת מחמש מעלות, תעד ואל תכייל עד שיסתדר.** פער בין 1.3 מעלות בסימולציה
לתוצאה גרועה יותר בחומרה הוא ממצא הנדסי אמיתי, וההסברים כבר כתובים ברשומה 8:
החזרי קול מהסביבה שהקירוב הגאוסיאני מתקשה איתם, וסף שלא כויל לסביבת הפריסה.

## בונוס — שתי בדיקות שכמעט חינם מאותה הרצה

השרת כבר רץ והאפליקציה יכולה להתחבר אליו, ולכן:

**D3, סיבוב בעקבות התראה.** כייל את הכיוון בתפריט הדשבורד, מחא כפיים מהצד, ולחץ SLEW
בכרטיס ההתראה. **הצריח אמור לזוז.** הנתיב מאומת בקוד: הפקודה מגיעה ל-
`ddl_bridge_handle_command`, שקורא ל-`ddl_servo_set_target` ומפרסם אירוע `NOISE_DETECTED`.
הקלט וידאו של הרצף.

**C4, נעילה על המטרה הנכונה.** באותה הרצה, הקש על תיבת זיהוי וודא שהמזהה שננעל
זהה למזהה שהוצג. עשר חזרות.

## האם צריך את הג'טסון

**לא, לא עבור הבדיקה האקוסטית.** המודול האקוסטי עצמאי לחלוטין ואינו נוגע במצלמה,
בזיהוי או בערוץ ה-ZeroMQ מול הג'טסון.

גם כשל של צינור המצלמה **אינו קטלני**. ב-`main.c` שורה 511 מופיע:

```
WARNING: camera pipeline failed to start at boot; will retry when an app connects
```

והשרת ממשיך. הגשר האקוסטי עולה בשורה 495, כלומר **לפני** המצלמה, ולכן הוא פועל
גם אם המצלמה או הג'טסון אינם זמינים.

**אבל אם הג'טסון פועל, השאר אותו פועל.** תקבל וידאו וזיהויים באותה הרצה, וזה מאפשר
לסגור באותו סשן גם את צילומי המסך, גם את בדיקת הנעילה וגם את בדיקת יציבות המזהים.
