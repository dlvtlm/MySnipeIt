**התקנה:**

**חלופה בלי שורת פקודה:** פשוט גרור את הקובץ ב-Android Studio מ-

לאחר מכן יש להוסיף שתי שורות, כמתואר בראש `LatencyProbe.kt`. האחת ב-`RaspberryPiClient.kt`

### 🟠 אם הפקודה `adb` אינה מזוהה

`adb` אינו ב-PATH כברירת מחדל בהתקנת Android Studio. יש שלוש דרכים, והשלישית
היא הפשוטה ביותר ואינה דורשת שורת פקודה כלל.

**דרך א, חלון Logcat של Android Studio — מומלץ, בלי שורת פקודה בכלל**

1. הרץ את האפליקציה על הטאבלט מ-Android Studio.
2. `View → Tool Windows → Logcat`, או Alt+6.
3. בשורת הסינון למעלה הקלד:
   ```
   tag:SnipeItLatency
   ```
4. בצע את הבדיקה, כלומר תן למערכת לרוץ עד שייאספו לפחות עשרים שורות.
5. סמן הכול ב-Ctrl+A, העתק ב-Ctrl+C, והדבק לקובץ
   `docs\chapter11\results\B2_latency_raw.txt`.

זה מייצר בדיוק את אותו קובץ שהפקודה `adb logcat` הייתה מייצרת, ולכן סקריפט
הניתוח `B2_analyze_latency.ps1` עובד עליו ללא שינוי.

**דרך ב, נתיב מלא ל-adb**

```powershell
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb devices
& $adb logcat -c
& $adb logcat -s SnipeItLatency > docs\chapter11\results\B2_latency_raw.txt
```

אם הנתיב אינו קיים, מצא אותו דרך
`File → Settings → Languages & Frameworks → Android SDK → Android SDK Location`,
והוסף לו `\platform-tools\adb.exe`.

**דרך ג, הוספה קבועה ל-PATH**

```powershell
$env:Path += ";$env:LOCALAPPDATA\Android\Sdk\platform-tools"
```

זה תקף לחלון הנוכחי בלבד. לקביעות, הוסף את אותה תיקייה דרך
`מאפייני מערכת → משתני סביבה → Path`.

### ❓ האם צריך לנעול על מטרה כדי שתוצג זווית הירי

**לא. אין שום צורך לנעול, ואפילו לא פעם אחת.**

`firingSolution` ב-`SniperViewModel.kt` מחושב מתוך `combine` על חמישה זרמים:
נתוני החיישנים המונצחים, מיקום ה-GPS של הטאבלט, גובה הטאבלט, והתחמושת והרובה
שנבחרו. **`selectedTargetId` אינו אחד מהם.** הנעילה משפיעה על מה שנשלח למכשיר
ועל צבע המסגרת בשכבת-העל, ולא על חישוב הזווית.

מה שכן נדרש, וכולו חייב להתקיים בו זמנית אחרת מוצג מקף:

| קלט | מאיפה | מה קורה אם חסר |
|---|---|---|
| מיקום GPS של הטאבלט | הרשאת מיקום + תפיסת לוויינים | `null`, אין פתרון |
| GPS של המכשיר, עם `valid` | מסגרת החיישנים | אין פתרון |
| כיוון מצפן, לא ריק ו-`valid` | מסגרת החיישנים | אין פתרון |
| זווית סרוו אנכית | מסגרת החיישנים | אין פתרון |
| **מד טווח, `valid` ומעל אפס** | מסגרת החיישנים | אין פתרון |

**החשוד המרכזי הוא מד הטווח.** הוא מחזיר `valid=false` כשאין החזר, כלומר כשהמערכת
מכוונת לשמיים או לטווח ארוך מדי. אם הזווית לא מוצגת, פתח את פאנל LIVE SENSORS
במסך הדיאגנוסטיקה, שמציג את הדגלים הגולמיים האמיתיים, ובדוק איזה מהחמישה שלילי.

**לבדיקת B2 עצמה זה לא רלוונטי**, משום ש-MOCK MODE מייצר את כל חמשת הקלטים
תקפים, ולכן הזווית מתעדכנת ברציפות ללא כל נעילה.

**ניתוח:**

```powershell
.\docs\chapter11\test-code\B2_analyze_latency.ps1
```

הסקריפט מדפיס מספר דגימות, ממוצע, חציון, אחוזון 95, מקסימום, מינימום וסטיית תקן,
משווה מול הסף של 2000 מילישניות, וכותב את הסיכום ל-`results\B2_latency_summary.txt`.

**ניקוי:**

```powershell
git checkout -- app\src\main\java\com\example\mysnipeit\data\network\RaspberryPiClient.kt
git checkout -- app\src\main\java\com\example\mysnipeit\viewmodel\SniperViewModel.kt
del app\src\main\java\com\example\mysnipeit\data\network\LatencyProbe.kt
```

**הסתייגות שחייבת להיכתב בפרק:** המדידה מבודדת את חלקה של האפליקציה בלבד.
ההשהיה מקצה לקצה, מרגע שהחיישן הפיזי מדד ועד שהערך מוצג, כוללת גם את מחזור הדגימה
בצד המכשיר ואת זמן הרשת. אין להציג את המספר הזה כאילו הוא ההשהיה המלאה.
הסקריפט מדפיס את המשפט הזה בסוף הפלט כדי שלא יישכח.

## תיקון 2 (בדיקה D5) — השהיית המודול האקוסטי

**מה זה מודד:** את הזמן מרגע זיהוי האירוע ועד שליחת הודעת ה-JSON.

**למה זה נדרש:** מפרט המודול קובע השהיה מתחת לחמישים מילישניות, אך **בקוד אין שום
מדידת זמן**. המספר נגזר בשלב התכנון ומעולם לא נמדד. ללא התיקון אין שום נתון השהיה
שניתן לדווח עליו בכנות.

**קובץ:** `test-code/D5_acoustic_timing.c.txt`

הקובץ מכיל שני מקטעי קוד להדבקה בתוך `acoustic_bridge_tick`, אחד לפני מקטע העיבוד ואחד
אחריו, יחד עם הוראות ההרצה והניקוי.

**המספר החשוב הוא `onset_to_emit` ולא `dsp`**, משום שהראשון מכסה גם את השהיית חוט
הלכידה ואת מסירת הדגל לחוט הראשי, וזה מה שהמפרט מדבר עליו.

**הערה שכדאי לכתוב בפרק:** תקופת העצירה של חצי שנייה אינה משפיעה על השהיית אירוע בודד,
משום שהיא חוסמת את הזיהוי הבא ולא את הנוכחי.

## תיקון 3 (בדיקה A7) — סקירת סף הזיהוי האקוסטי

**מה זה מודד:** את יחסי הגומלין בין הסף `ONSET_THRESHOLD` לבין שיעור הזיהוי ודיוק הזווית.

**קובץ:** `test-code/A7_threshold_study.sh`

הסקריפט אוטומטי לחלוטין. הוא סורק שישה ערכי סף כפול ארבע רמות רעש, בונה מחדש בכל שלב,
**ומחזיר את הקובץ המקורי גם אם נעצר באמצע**. אין צורך בעריכה ידנית.

```bash
sudo apt install build-essential libfftw3-dev
cd acoustic_detection_v2/acoustic_detection
/path/to/docs/chapter11/test-code/A7_threshold_study.sh
```

**מה מחפשים בפלט:** את השורה שבה שיעור הזיהוי מגיע למאה אחוז אך שגיאת הזווית הממוצעת
קופצת לעשרות מעלות. במדידה שכבר בוצעה זה קרה ברעש 0.10 ובסף 1.2, עם שגיאה ממוצעת של
73.2 מעלות. זו ההדגמה החדה ביותר לכך שגלאי רגיש מדי אינו מתדרדר בהדרגה אלא מייצר
תשובות שגויות בביטחון מלא.

## תיקון 4 (בדיקה A8) — שחזור השוואת מדדי הביטחון

**מה זה מודד:** את המדד הנטוש מול המדד הנוכחי על אותם נתוני קלט בדיוק.

**קובץ:** `test-code/A8_confidence_compare.c.txt`

**צפוי:** המדד הישן בתחום 0.003 עד 0.016, החדש בתחום 0.84 עד 0.89. מאחר ששער התקפות
הוא ביטחון גבוה מ-0.3, המשמעות היא שכל אירוע היה משודר עם דגל תקפות שלילי למרות זווית
מדויקת, כלומר כשל שקט מוחלט.

**למה בכל זאת שווה להריץ:** מסמך התשובות של המודול האקוסטי מציין במפורש שהמספרים שם
הם **שחזורים שנעשו בדיעבד ולא תצפיות שנרשמו בזמן אמת**. הרצה עצמאית שלך הופכת אותם
לתוצאה שאתה יכול להגן עליה.
